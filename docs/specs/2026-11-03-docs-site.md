# Documentation site — design

**Status:** designed 2026-11-03, not built. This is the second half of the docs pass; the
first half, numpy docstrings for the whole public API, shipped in #50. Marks:
**[decided]** was settled with the maintainer; **[call]** was settled by the designer and
is open to objection; **[builder]** is left to whoever builds it.

---

## 1. Intent

The site should be the best documentation a Discord bot library has. The model is
lightbulb's [by-example pages](https://hikari-lightbulb.readthedocs.io/en/3.2.5/by-example.html):
they walk through every concept of the framework, the hard ones included, with little
text, many examples and short chapters that each stand on their own. risa's site does the
same and goes further in two ways:

- **Every example shows what it looks like in Discord.** The rendered message sits right
  under the code. Lightbulb never shows its output.
- **The hard concepts get diagrams.** Where state lives, what a click goes through, what
  happens to old messages: these are easier to see than to read.

It also has to look like risa. The maintainer made a logo, a mascot (Risa) and a banner,
and the site is built around them.

## 2. Readers [decided]

Two kinds, equally important:

- **New bot developers** building their first buttons. The walkthrough starts from zero:
  what a component is, why a click arrives later as its own event, why there are three
  seconds to answer. It explains these through risa, not as a general Discord course.
- **People coming from miru.** They get a page of their own (§4.2) and small notes inside
  the chapters (§5) that say what was different in miru. The big difference leads: every
  risa view survives a restart, with no `timeout=None`, no fixed custom_ids and no
  re-registering at startup.

## 3. Goals, non-goals, anti-goals

**Goals:** every concept covered by example, in a fixed order; short prose; real,
checked examples; a Discord preview for every example; static diagrams for the hard
concepts; a look built on the maintainer's art; dark first.

**Non-goals:**

- A separate "Guides" section. Everything a guide would say lives in a chapter. [decided]
- Animated or interactive diagrams. Mockups of a step-through animation and a clickable
  custom_id explorer were shown and turned down; diagrams are static. [decided]
- Translations, a changelog page, a blog. English only until 1.0. [call]

**Anti-goals, which would make the site a failure even if it works:**

- **Altered artwork.** The logo, the logo with Risa and the banner are used as the files
  the maintainer made. Nothing is cropped, recoloured, cut apart or composed from parts
  (§7.3). [decided]
- **Risa's face as decoration in content**, such as on tip boxes. Shown in a mockup and
  rejected. [decided]
- **White as the only mode, or white backgrounds at all.** [decided]
- **Walls of text** where an example or a diagram would do.
- **Examples or previews that drift from the code.** An example that no longer runs, or a
  preview that shows something the code would not render, is worse than none (§6).

## 4. Structure

### 4.1 Navigation [decided]

Three sections: **Get started · By example · API**. The landing page sits in front of
them.

### 4.2 Get started [decided]

- **Installation.** `uv add hikari-risa` and `pip install hikari-risa`, and the extras
  `[redis]`, `[postgres]` and `[radixly]`. Until the first release the page also shows the
  install from GitHub (`uv add git+https://github.com/rayakame/hikari-risa`), since `main`
  is online before the package is on PyPI.
- **Your first view.** The counter (§4.4) end to end, with sending it shown in three tabs:
  with lightbulb (`risa.client_from_lightbulb`), with plain hikari on the gateway, and as
  a REST bot (`risa.client_from_app` in both).
- **Coming from miru.** It maps what a miru user knows onto risa: the view class, items
  as handler methods, `ViewContext` versus `ComponentContext`, starting a view versus
  `client.build`, persistent views versus every view being restart-proof, `timeout`
  versus `ttl` on `InStore`. **[builder]** verify every miru claim against miru's current
  documentation; do not write it from memory.

### 4.3 By example [decided, the order a call]

The walkthrough. Each chapter is one page and builds on the ones before it.

| # | Chapter | Covers |
|---|---|---|
| 01 | Views | a view class, `render()`, `@risa.register`, the `ui` nodes `Container`, `TextDisplay`, `Row`, `Button`; sending with `client.build` |
| 02 | Buttons that remember | durable fields; state travelling in the message; a restart changes nothing |
| 03 | Handlers and arguments | `@risa.handler` with id, version and `defer`; `risa.bind()` and wire arguments; wire enums are stdlib `enum.Enum` only, so a hikari enum is passed as `int`/`str` and rebuilt in the handler |
| 04 | Selects, sections, galleries | the selects, `Section` with its accessory, `Thumbnail`, `MediaGallery`, `Separator`, `File`, `LinkButton`; V1 as the special case of a tree of rows |
| 05 | Answering in time | the three-second window; `respond`, `defer`, `acknowledge`, `rerender()`, `edit(layout)`; `AutoDefer` and which mode pairs with which verb (THINKING with `respond()`, UPDATE and OFF with `rerender()`) |
| 06 | Fresh data with Prop and load() | `risa.Prop[T]`, `load()`, injection into `load()` |
| 07 | How much fits in a message | capacity; `StateOverflowError` and its per-field breakdown, which risa does not have yet (see below) |
| 08 | Where state lives | `InMessage` versus `InStore`; the decision rule; the placement 2×2; the world-readable warning |
| 09 | Stores and TTL | `MemoryStore`, `RedisStore`, `PostgresStore`; what `ttl` means and `ttl=None`; Redis `maxmemory-policy` and AOF; Postgres sweeps |
| 10 | Changing a view safely | view and handler versions; `on_outdated`; the rejection handler as its precise alternative; `on_state_missing` |
| 11 | Dependency injection | linkd; sharing one manager with lightbulb; `ctx` is positional, so handlers work with DI off |
| 12 | Several processes | gateway versus multi-process REST; the in-process lock, the lease lock and the compare-and-set; last-write-wins for `InMessage` |
| 13 | Writing your own store | the `Store` protocol and `verify_store` |

Sources for the content: `DESIGN.md` (§6.4 for the rejection handler, §7 for state, §8
for responses, §10 for the 2×2 and the Redis notes), the "Notes that outlive the current
step" in `HANDOFF.md`, and the docstrings, which already carry most of these notes in
short form.

**The growing poll [call].** From chapter 07 on, one example runs through the chapters: a
poll that records who voted.

- In 07 the list of voters grows until the poll hits the capacity limit, and the error
  says which field takes how much. **[builder]** measure the real limit; do not guess it.
- In 08 the poll is the case for `InStore`, and the voter IDs are where the world-readable
  warning appears, at the point of use.
- In 09 it moves to a store, first `MemoryStore` with its startup warning, then
  `RedisStore`.
- In 10 it first gains a field with a default, which is free: old polls keep working
  (DESIGN §7.6). Then it makes a change that is not free, such as changing what a vote
  records; its `version` goes up, and old polls reach `on_outdated`.

Chapters 01 to 06 have small examples of their own.

**The per-field breakdown is built first [decided].** DESIGN §13 promises that
`StateOverflowError` says how much each durable field takes, but today the error carries
only `needed`, `available`, `slots` and the codec. It is built into risa as its own pull
request, with its own small design, before chapter 07 is written.

### 4.4 Landing page [decided]

From top to bottom, with no sidebar:

1. The top bar: section links, search, the mode switch.
2. **`banner.png` across the full width.**
3. The tagline, "Components V2 views for hikari, with state that survives restarts.", with
   its second half in the pink-to-lavender gradient, and two sentences under it.
4. Buttons "Get started" and "Learn by example", and the install command.
5. The counter, its code beside its Discord preview, with the note that a restart leaves
   the count where it was.
6. Three cards: survives restarts; Components V2 first; typed all the way.
7. A card linking to "Coming from miru".

The counter, as in the first chapters:

```python
@risa.register(name="counter")
class Counter(risa.View):
    count: int = 0

    def render(self) -> ui.Layout:
        return ui.Container(
            ui.TextDisplay(f"Clicked **{self.count}** times"),
            ui.Row(ui.Button(self.click, label="+1")),
        )

    @risa.handler
    async def click(self, ctx: risa.ComponentContext) -> None:
        self.count += 1
        await ctx.rerender()
```

### 4.5 API reference [call]

One page per public module (`risa`, `risa.ui`, `risa.state`, `risa.store`,
`risa.store.redis`, `risa.store.postgres`, `risa.store.testing`, `risa.codecs`,
`risa.errors`, `risa.di`), generated from the numpy docstrings, in the site's look, with
types in signatures linked.

## 5. Chapter anatomy [decided]

- **Title and one lead sentence** saying what the chapter makes possible.
- **Short sections.** One to three sentences of prose, then code of at most about 15
  lines, then directly under it the Discord preview, joined to the code as one block
  labelled "In Discord".
- **Diagrams** where a picture explains more than prose (§7.6).
- **Tips** as boxes with a pink border and no face. **Warnings**, such as the
  world-readable one, in a colour of their own. [call: amber]
- **"In miru …" notes** where a miru user would expect something else: one or two
  sentences, visually quieter than a tip.
- **The full file.** Under the excerpt, a collapsed block opens the complete runnable
  file (§6).

## 6. Examples and previews

- **Every example is a real file** under `docs/examples/`, one per chapter step, complete
  with imports and client setup. The page shows an excerpt and the collapsed full file.
  ruff and pyright check these files in CI like library code, so an example that drifts
  from the API fails the build. [decided]
- **Previews come from the real code.** A build step imports each example, builds its view
  with risa, and turns the resulting component payload into the preview's HTML. A page
  includes the generated HTML; nobody writes a preview by hand. [decided] How the step
  hooks into the build, for example a script run by the `docs` nox session before
  `zensical build`, with the pages pulling the fragments in through snippets, is
  **[builder]**. Zensical's plugin support is not MkDocs', so the step should not depend on
  an MkDocs plugin.
- **The preview is Discord's dark theme**: background `#313338`, container `#2b2d31` with
  the container's accent colour as the left bar, text `#dbdee1`, primary buttons
  `#5865f2`. It is the same in both site modes. The bot is called "Risa Bot", with the
  APP tag and `assets/avatar.png` as its avatar. [decided]
- **What a preview shows [call].** A view as `client.build` renders it. A page that needs
  the state after a click shows a second preview, built from the same view with the
  fields the click leaves behind (`Counter(count=4)`). A reply that is not a view, such
  as an ephemeral "pong" or Discord's "thinking…" placeholder, is drawn by the same
  preview component from a few lines of data next to the example, never from
  hand-written HTML. No click is simulated through the dispatcher. Chapter 07 shows the
  `StateOverflowError` text that building the overflowing poll actually raises.
  Chapters 11 to 13 have nothing new to see in Discord and no preview.
- **Which components the preview must draw** follows from the chapters: everything in
  `risa.ui` that chapters 01 to 10 use. Where a component would be expensive to draw
  faithfully (a media gallery with real images), a plain stand-in that keeps the layout is
  fine. **[builder]**
- **The example files follow the library's rules [call]**, the 19-line MIT header
  included, with the per-file ignores the tests have (`D`, `DOC`, `S101`, `PLR2004`) plus
  `INP001`. The page shows excerpts and the full file without the license header.

## 7. Look

### 7.1 Modes [decided]

- **Dark is the default**, on first visit, whatever the operating system prefers. A switch
  at the top right changes to light, and the choice is remembered.
- **Dark ("Night"):** near-black violet with pink as the glowing accent and soft light
  behind the content.
- **Light ("Banner tone"):** lavender to cherry-blossom pink, taken from the light side of
  the banner. Never white.
- **Code blocks are dark in both modes**, with the same syntax colours, so code looks the
  same everywhere and the step down into the Discord preview does not jump.

PNG or JPEG since GitHub takes no WebP there. The copies live in `assets/` next to the

navigation. The top bar of a chapter page carries only search and the mode switch.

### 7.4 Small screens [decided]

The sidebar, logo included, moves into a drawer. A slim top bar stays, with the small
logo: `logo-light.svg` in dark mode, `logo.svg` in light mode. **[builder]** which of the
two the favicon uses, given that browsers draw tabs both light and dark.

### 7.5 Type [decided]

Inter for text, JetBrains Mono for code. **[call]** self-hosted, so the site makes no
requests to Google Fonts.

### 7.6 Diagrams [decided]

Static, in the style of the approved mockup: rounded cards on the code-block surface
(`#1a0f2c`, border `#2d1c48`), each with a small pink step number, a bold title and one
line of detail. Pink arrows connect them. Monospace values are in `#ffd479`. Diagrams must
work in both modes and stay readable on a phone, where a row of cards stacks. Not Mermaid:
it cannot take this look. **[builder]** whether they are HTML/CSS components or SVG.

Diagrams the content needs at least:

- the path of a click: click, read the id, find the view, unpack the state, run the
  handler, rerender, with the real custom_ids of the counter (chapter 02 or 05)
- how a view's state sits across the custom_ids of its components (chapters 02 and 07)
- the placement 2×2 (chapter 08, DESIGN §10)
- what happens to an old message when a view changes (chapter 10)
- the lock and compare-and-set across processes (chapter 12)

Real custom_ids come from risa itself, never written by hand.

## 8. Tooling and hosting

- **Generator:** Zensical with mkdocstrings-python for the API reference, pinned in a
  new `docs` dependency group (at design time Zensical 0.0.74 and mkdocstrings-python
  2.0.10). Zensical is the successor to Material for MkDocs, which stops receiving fixes
  on 2026-11-05. The look is built with Zensical's extra CSS and, where the page frame
  must change, template overrides. Overrides follow Zensical's advice to override
  `main.html` rather than `base.html`. [call]
- **Config:** `zensical.toml` beside `pyproject.toml`; page sources in `docs/`.
  `docs/specs/` must not be published. [call]
- **Build check:** a `docs` nox session runs the preview step (§6) and `zensical build`,
  and joins the default `nox` run, so a broken page, reference or example fails locally
  and in CI. [call]
- **Hosting:** GitHub Pages at `rayakame.github.io/hikari-risa`, served from the `gh-pages`
  branch and versioned: `main/` follows the main branch and is online right away, each minor
  release has a folder that its patch releases replace, and `stable/` is a copy of the newest
  release. A version selector (`extra.version` with provider `mike`, drawn from `versions.json` in
  mike's format) lists them, and every version but `stable` shows a banner pointing to the
  latest release. The root redirects to `stable/` once a release exists and to `main/` before,
  and until then `main` carries the `stable` alias in `versions.json` so that it shows no
  banner. The root also serves the default version's `404.html`.
  mike itself is not used: it only runs `mkdocs build` from a YAML config, and Zensical reads
  just `versions.json`, so `tools/docs/publish.py` does mike's job. The workflow
  `docs.yml` builds on every push to main and every published release, then publishes into
  `gh-pages`. Pull requests build and check the site without publishing. **[decided]**
  2026-11-03. [call: GitHub Pages]
- **README:** short. The banner, one sentence, the counter, the install command, a link to
  the site. CONTRIBUTING.md stops claiming the package is on PyPI until it is. [call]
- **Work split:** how the build is cut into pull requests. **[builder]**
