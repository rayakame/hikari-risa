# Modals — design

**Status:** designed 2026-10-25 to 2026-10-31, not built. **Building waits for hikari** to
parse the new modal components (§2). This document supersedes the modal design that stood
in `DESIGN.md` §9 until 2026-10-31; §9 now points here, and for modals this document is the
authority. Marks: **[decided]** was settled with the maintainer; **[call]** was settled by
the designer and is open to objection; **[builder]** is left to whoever builds it.

---

## 1. Intent

A modal in risa is one self-contained class. The class declares what the form asks,
`render()` draws the form the way a view draws its message, and `on_submit` handles the
answer. The bot passes data in through the constructor; what the user answered comes back
through `ctx`, never through `self`.

Three things drive the design:

- **Restart-safe by construction.** The submit is an ordinary fresh dispatch. Nothing about
  an open form lives in process memory: the modal's own fields ride its `custom_id`, and a
  form opened from a view reaches that view's state through the normal session machinery.
  A form opened before a restart, or answered on another REST process, still works.
- **The 2025–2026 modal components.** Discord added Label, Text Display, selects, File
  Upload, Radio Group, Checkbox Group and Checkbox to modals. They need configuration
  (options, descriptions, file types) that often comes from runtime data (the current
  options of a poll). A field declaration cannot carry that; a render pass can.
- **Typed end to end.** pyright strict checks that a node gets an input of the right kind,
  that optionality agrees, and that a result is used at its real type (§8.1).

What a bot developer writes:

```python
@risa.register(name="poll", version=1)
class Poll(risa.View):
    options: list[str]

    @risa.handler
    async def rename(self, ctx: risa.ComponentContext, index: int) -> None:
        await ctx.prompt(RenameOption(index=index, current=self.options[index]))


@risa.modal(name="rename-option", version=1, defer=risa.AutoDefer.UPDATE)
class RenameOption(risa.ViewModal[Poll]):
    name = risa.Input[str]()
    notify = risa.Input[bool]()

    index: int
    current: risa.Prop[str] = ""

    def render(self) -> risa.Form:
        return risa.Form(
            ui.TextDisplay(f"You are renaming **{self.current}**."),
            ui.Label("New name", ui.TextInput(RenameOption.name, value=self.current, max_length=50)),
            ui.Label("Notify voters", ui.Checkbox(RenameOption.notify)),
            title="Rename option",
        )

    async def on_submit(self, ctx: risa.ViewModalContext[Poll]) -> None:
        async with ctx.origin() as poll:
            if ctx.changed(RenameOption.name):
                poll.options[self.index] = ctx.value(RenameOption.name)
        if ctx.value(RenameOption.notify):
            ...
```

And a form opened from a command, with no view behind it:

```python
@risa.modal(name="feedback", version=1, defer=risa.AutoDefer.THINKING_EPHEMERAL)
class Feedback(risa.Modal):
    subject = risa.Input[str]()
    details = risa.Input[str | None]()

    guild_id: int

    def render(self) -> risa.Form:
        return risa.Form(
            ui.Label("Subject", ui.TextInput(Feedback.subject, max_length=80)),
            ui.Label("Details", ui.TextInput(Feedback.details, required=False, paragraph=True)),
            title="Feedback",
        )

    async def on_submit(self, ctx: risa.ModalContext, db: Database = linkd.INJECTED) -> None:
        await db.store_feedback(self.guild_id, ctx.value(Feedback.subject), ctx.value(Feedback.details))
        await ctx.respond("Thanks!")


# inside a lightbulb slash command
await ctx.respond_with_modal(**await risa_client.build_modal(Feedback(guild_id=ctx.guild_id)))
```

## 2. Prerequisite: hikari must parse the new components

**[decided]** Modals wait until hikari supports the new modal components. Building on
today's hikari would ship only legacy text inputs and put the new components on paper.

What stands today:

- **hikari 2.6.0** (the pinned version) sends any `ComponentBuilder` in a modal response,
  so a Text Display can be sent. On submit, `EntityFactory._deserialize_modal_components`
  keeps only top-level `ACTION_ROW`s with legacy text inputs and drops everything else with
  a DEBUG log. An input wrapped in a Label is therefore lost on submit.
- **hikari PR #2489** ("Add support for new modal option types",
  `mplatypus/feature/modals-v2`, open, last updated 2026-08-07) adds
  `LabelComponentBuilder` (label, description, one child), `FileUploadComponentBuilder`,
  `is_required` on selects, the deprecation of `TextInput.label`, interaction components
  for Label, TextInput, the selects and FileUpload, `ModalInteraction.components` typed
  over them, and `ModalInteraction.resolved`. **It does not cover Radio Group, Checkbox
  Group or Checkbox.**

What risa needs from hikari before building:

| Needed | In #2489 |
|---|---|
| Label builder with description and one child | yes |
| Submit parsing of Label → child, with each input's `custom_id` and value | yes |
| Text Display accepted in a modal | sending already works on 2.6 |
| Text, user, role, mentionable and channel selects in a Label, `is_required` | yes |
| File Upload builder, submitted attachment ids, `ModalInteraction.resolved` | yes |
| Radio Group, Checkbox Group, Checkbox builders and submit parsing | **no** |

If hikari ships the components in parts, build what hikari parses; the missing nodes are
additive and change no bot code (§4.4).

Discord facts the design rests on (from the components reference and change log; the
Label, File Upload, Radio and Checkbox details came from a summary and are to be checked
against the reference before building):

- A modal holds 1–5 top-level components; the title is at most 45 characters.
- Label (type 18): `label` ≤ 45, `description` ≤ 100, exactly one child. Inputs must sit
  in a Label; an ActionRow holding a TextInput is deprecated in modals, as is
  `TextInput.label`.
- Text Display (10) is allowed at the top level of a modal.
- String Select (3): ≤ 25 options, `min_values`/`max_values`, `required`; submits
  `values: list[str]`. User/Role/Mentionable/Channel selects (5–8): `default_values`;
  submit snowflakes plus `resolved`.
- File Upload (19): ≤ 10 files, `file_types`; submits attachment ids plus `resolved`.
- Radio Group (21): 2–10 options; submits `value: str | null`.
  Checkbox Group (22): 1–10 options; submits `values: list[str]`.
  Checkbox (23): submits `value: bool`; it cannot be required.
  (Released 2026-02-12. Label 2025-08-25, selects in modals 2025-09-10, File Upload
  2025-10-15.)
- Every interactive component carries its own `custom_id` of 1–100 characters; the submit
  nests Label → `component`.
- A modal submit cannot be answered with another modal.

## 3. Goals, non-goals, anti-goals

**Goals**

- One class per form: inputs, look and submit handling in one place.
- Works without a view (`risa.Modal`, opened from a command) and on top of one
  (`risa.ViewModal[V]`, opened from a view's handler, with locked access to its state).
- Every modal component Discord offers becomes a node; adding one later changes no bot code.
- Restart-safe and multi-process-correct with no infrastructure.
- pyright strict catches binding and type mistakes before the bot runs.

**Non-goals (deliberately not in this work)**

- Opening a modal from a command. risa handles no commands; it builds the modal and the
  command framework sends it (`build_modal`).
- Converting text input (`Input[int]` for a text field). See §4.4.
- Enum-typed radio groups and selects (`Input[Color]` with `options=Color`). Fine to add
  later as an overload; nothing breaks.
- A "button opens this form directly" shortcut. Later.
- `load()` on modals, and modal state in a `Store`.
- `prompt_wait` (an inline `await` for the submit). Investigated and rejected for stateful
  views; see §7.
- `ctx.reserve(name, ttl=)`. Still deferred (DESIGN §15).

**Anti-goals (would make this a failure even if it worked)**

- risa answering end users in the bot's voice. Unhandled cases get no answer and a log
  line, exactly as `on_outdated` and `on_state_missing` behave today.
- Two ways to declare a form (an automatic form for simple cases plus `render()` for the
  rest). `render()` is the only way.
- Instance fields that double as user answers.
- Binding nodes to inputs by string.
- A table of Discord layout limits (CONTRIBUTING.md, "Discord's layout limits are
  deliberately not policed").

## 4. The developer surface

### 4.1 Three kinds of class members **[decided]**

| Member | Written as | What it is | Where its value comes from |
|---|---|---|---|
| Input key | `name = risa.Input[str]()` (no annotation) | what the form asks: a name and a result type, no value | — |
| Durable field | `index: int` | data the bot passes in | the constructor at open; the modal's `custom_id` at submit |
| Prop | `current: risa.Prop[str] = ""` | data only `render()` needs | the constructor at open; its default at submit |

- Input keys are plain class attributes, so msgspec does not treat them as fields and the
  constructor does not take them. A key learns its name from `__set_name__`.
- Durable fields and Props follow the view rule (DESIGN §7.2): fields are durable by
  default, `risa.Prop[T]` marks the fresh ones, and a Prop must have a default. A Prop is
  not refilled at submit (there is no `load()`), so it holds its default there.
- **The modal instance never holds a user's answer.** Answers come from `ctx.value(key)`.
- The constructor is keyword-only. **[call]**

### 4.2 `render()` is mandatory **[decided]**

`render(self) -> risa.Form` builds the form from nodes, exactly as `View.render` builds a
message. `risa.Form(*nodes, title=...)` holds the top-level nodes and the title.

- The title lives in `Form`, so a dynamic title is plain code
  (`title=f"Rename {self.current}"`) and the decorator takes no title. **[call]**
- `render()` runs once, when the form is built for sending. It does not run at submit.
- Leaving an input out of the form is allowed (conditional fields). An input that appears
  twice in one form is an error when the form is built. **[decided]**

### 4.3 Declaring and registering **[call]**

`@risa.modal(name: str, version: int = 1, defer: risa.AutoDefer | None = None)` mirrors
`@risa.register`:

- The name is unique among modals, registered in the global registry; `client.add_modal(cls)`
  mirrors `client.add_view`, and `use_global` covers modals the same way it covers views.
- Bump `version` when durable fields or input keys change incompatibly. A form opened
  before the bump and submitted after it routes to the modal's `on_outdated` hook (§4.9).

### 4.4 Nodes and value types **[decided]**

Input nodes take the key as their first argument; the key type fixes what `ctx.value`
returns.

| Node | Key | Notes |
|---|---|---|
| `ui.TextInput` | `Input[str]`, or `Input[str \| None]` with `required=False` | empty optional input arrives as `None`; prefill via `value=` |
| `ui.RadioGroup` | `Input[str]`, or `Input[str \| None]` with `required=False` | |
| `ui.CheckboxGroup` | `Input[Sequence[str]]` | "nothing chosen" is an empty sequence; `min_values` on the node |
| `ui.TextSelect` (in a modal) | `Input[Sequence[str]]` | as above |
| `ui.Checkbox` | `Input[bool]` | Discord does not allow it to be required |
| user/role/mentionable/channel selects | hikari objects from `resolved` | exact types **[builder]** |
| `ui.FileUpload` | attachments from `resolved` | exact types **[builder]** |
| `ui.TextDisplay` | — | static Markdown |
| `ui.Label(label, child, description=...)` | — | wraps exactly one input |

- **Optionality is stated twice, and pyright checks they agree [decided].** The key type
  says `| None`; the node says `required=False`. Overloads on the node constructors plus an
  invariant `Input[T]` make every mismatch a pyright error (verified, §8.1). There is no
  runtime reading of the key's type parameter.
- **Text input always yields `str` [decided].** A conversion that can fail has nowhere to
  report its failure: Discord forbids answering a submit with another modal, so the form
  cannot reopen with an error, the typed text would be lost, and risa would have to speak
  for the bot. The developer converts and answers the user.
- `ui.TextInput` takes `paragraph: bool = False` for the multi-line style; `risa.Paragraph`
  and `Annotated[str, risa.TextInput(...)]` no longer exist. **[call]**
- Options for radio, checkbox groups and text selects follow the existing
  `ui.SelectOption` shape (label, value, description, emoji, default), and a prefill is an
  option marked default. **[call]** The examples here pass plain strings for brevity.

### 4.5 Opening a form **[decided]**

| | opens `risa.Modal` | opens `risa.ViewModal[V]` |
|---|---|---|
| `await risa_client.build_modal(modal)` | yes | no (pyright rejects it) |
| `await ctx.prompt(modal)` in a risa handler | yes | yes |

- `build_modal` returns the modal counterpart of `ui.Rendered`: a mapping of `title`,
  `custom_id` and `components`, so `**` spreads it into hikari's `create_modal_response` or
  lightbulb's `respond_with_modal`. It is async, mirroring `client.build`. **[call]**
- `ctx.prompt` exists on `ComponentContext` only. It must be the click's first response:
  if the auto-defer watchdog has already acknowledged the click, Discord forbids a modal,
  and `ctx.prompt` raises `risa.AlreadyRespondedError` naming `defer=risa.AutoDefer.OFF`
  as the fix. With the default `OFF` this cannot happen. **[call]**
- For a `ViewModal[V]`, `ctx.prompt` checks at runtime that the message's view is an
  instance of `V` (works for unions and shared base classes); a mismatch there is a
  programming error and raises. At submit, a message that no longer holds a `V` is the
  origin-gone case (§4.7).
- **The REST listener slot:** hikari's interaction server keeps one listener per
  interaction kind, and lightbulb's REST client takes the component and modal slots when it
  is built. For components, #44 made risa share the slot (DESIGN §11): it takes the slot,
  hands every interaction it does not adopt to the previous holder, and warns once unless
  `warn_shared_listener=False`. The modal listener does the same for `ModalInteraction`
  (§11).

### 4.6 The submit **[decided]**

```python
ctx.value(RenameOption.name)                   # str
ctx.value(Feedback.details)                    # str | None
ctx.value(RenameOption.notify, default=False)  # bool, also when the checkbox was left out of the form
ctx.changed(RenameOption.name)                 # bool
```

- `ctx.value(key)` returns the submitted value at the key's type. If the input was not in
  the form, it raises `risa.InputMissingError` naming the input; with `default=` it
  returns the default instead.
- `ctx.changed(key)` says whether the user changed the input from its prefill. risa writes
  the input key and a 4-character fingerprint of the prefill into each input's own
  `custom_id` and compares it with the submitted value.
  - unchanged → `False`; empty prefill, typed text → `True`; optional input emptied →
    `True` and the value is `None`.
  - Works for command-opened forms too, and anywhere in `on_submit`.
  - A key that was not in the form raises `risa.InputMissingError`.
- **No staleness check in risa [decided].** The view may change while a form is open; the
  submit edits only what the user changed (`ctx.changed`), and two users changing the same
  input means the last submit wins. A developer who must know whether someone else changed
  a value in the meantime keeps the old value in a durable field (`old_title: str`) and
  compares inside `ctx.origin()`; that costs `custom_id` space.
- DI: `on_submit` is injected through linkd inside `Contexts.DEFAULT` nested with
  `Contexts.MODAL`; `ctx` is positional, so it works with DI disabled. **[call]**
- An exception from `on_submit` is logged at ERROR, as for handlers. **[call]**

### 4.7 `ViewModal` and `ctx.origin()` **[decided]**

`ViewModalContext[V]` adds the message, `edit`, `origin()` and `rerender()`.

```python
async with ctx.origin() as poll:   # poll: V, freshly loaded, locked
    poll.options.append(...)
```

- **Enter:** take the view's lock, load its state fresh, run `load()`.
- **Normal exit:** the same rule as a click's clean exit (DESIGN §7.4). If the state
  changed, risa commits and rerenders the origin message, which answers the submit if
  nothing else has. If it did not change, nothing is written and nothing is answered. A
  form that can be submitted unchanged therefore sets `defer=risa.AutoDefer.UPDATE`
  (§4.8), exactly as a click handler that may change nothing does. **[decided 2026-11-01]**
- **Exception:** no commit, the lock is released, the exception propagates.
- `ctx.rerender()` works only inside the block.
- **State missing or view outdated on enter:** the message still holds a `V`, but its
  state cannot be read. `ctx.origin()` raises (the missing-state error, or an outdated
  error). Caught, the form answers the user itself. Uncaught, risa runs the view's
  `on_state_missing` / `on_outdated` hook with this context, the same hook a click would
  reach. There is no switch on `origin()`; the `try` is the switch.
- **Origin gone:** the message no longer holds a current `V`. Three routine races while the
  form is open cause it: the view was closed (a terminal `edit` removed its components), a
  deploy bumped `V`'s version (the old cookie resolves to nothing), or the message now
  shows another view. In all three, `ctx.origin()` raises `risa.OriginGoneError`. Caught,
  the form answers the user itself. Uncaught, risa runs the **modal's** `on_outdated`
  (§4.9), since no view is left whose hook could run. **[decided 2026-11-01]**
  - The log names which of the three it was. All three are visible from the message
    itself, so the modal's `custom_id` carries nothing extra for this. **[call]**
- Error names **[builder]**: reuse `StateNotFoundError` if it fits, add an outdated error
  and `OriginGoneError` in `risa/errors.py` following its pattern.

### 4.8 Answering the submit **[decided]**

Discord expects an answer within 3 seconds. What it allows depends on where the form was
opened:

| Opened from | Allowed answers |
|---|---|
| a button or select | send a message, update the message, or acknowledge silently |
| a slash command | send a message, possibly deferred ("thinking"); no silent acknowledgement |

Modals get the same `defer=risa.AutoDefer...` knob as clicks, with the same meaning and the
same default `OFF`: per modal on `@risa.modal(defer=)`, otherwise the client's default.

- A `ViewModal` was always opened from a message, so `UPDATE` always works. The rerender at
  the end of `ctx.origin()` answers only a submit that changed the state (§4.7); `UPDATE`
  answers the rest silently.
- A command-opened `Modal` with `UPDATE`: Discord forbids the silent acknowledgement, so
  risa skips it and logs a WARNING that a command-opened form must be answered with a
  message. `THINKING` and `THINKING_EPHEMERAL` work there.
- `on_submit` finishes without answering: under `OFF` risa sends nothing; otherwise it
  sends the silent acknowledgement, both as for clicks (DESIGN §8.1). A command-opened form
  cannot take that acknowledgement either, so there risa skips it with the same WARNING.
  **[call]**
- risa tells the two apart from the submit itself: `ModalInteraction.message` is the
  message whose component opened the form, and `None` for a command-opened one.

### 4.9 Outdated forms

A submit whose modal `custom_id` names a known modal but an old version or an
undecodable schema routes to the modal's `on_outdated(cls, ctx: risa.ModalContext)` hook.
The default sends nothing and logs a WARNING suggesting the override, as views do. **[call]**
An uncaught `OriginGoneError` from a `ViewModal` reaches the same hook (§4.7); a form that
wants a different answer for a gone origin catches the error in `on_submit`.
A submit whose `custom_id` risa does not recognise is ignored silently, so risa coexists
with other modal handlers.

## 5. Contexts and the modal class family **[decided]**

### 5.1 Python 3.13

The floor goes from 3.12 to 3.13, for type-parameter defaults (PEP 696). This touches
`requires-python`, the ruff target, pyright's `pythonVersion`, the nox/CI matrix, the
classifiers and the toolchain table in `CONTRIBUTING.md`.

### 5.2 Contexts

```python
class Context[T: hikari.ComponentInteraction | hikari.ModalInteraction = (
    hikari.ComponentInteraction | hikari.ModalInteraction
)]: ...

class ComponentContext(EditMixin, Context[hikari.ComponentInteraction]): ...
class ModalContext(Context[hikari.ModalInteraction]): ...
class ViewModalContext[V: View](EditMixin, ModalContext): ...   # origin() -> V
```

- Hooks that can be reached from a click and from a submit (`on_outdated`,
  `on_state_missing`) take a bare `ctx: risa.Context`, which the default makes legal under
  pyright strict.
- The edit capability (`message`, `edit(layout)`, `rerender()`) has two users,
  `ComponentContext` and `ViewModalContext`, so it lives in a mixin. Its exact split
  **[builder]**.

### 5.3 Modal classes

```python
class BaseModal[C: ModalContext](msgspec.Struct, kw_only=True):
    def render(self) -> risa.Form: ...
    async def on_submit(self, ctx: C) -> None: ...

class Modal(BaseModal[ModalContext], kw_only=True): ...
class ViewModal[V: View](BaseModal[ViewModalContext[V]], kw_only=True): ...
```

- `BaseModal` holds the shared logic (schema, wire, keys) and is public, so helpers can be
  typed against it. **[call]**
- `ViewModal` cannot be a subclass of `Modal`: its `on_submit` takes a narrower context,
  which pyright reports as an incompatible override (§8.2).
- `ViewModal[Poll | Quiz]` is supported; `ctx.origin()` yields `Poll | Quiz` and `match`
  narrows it.

## 6. Wire format **[builder, within these rules]**

- **The modal's `custom_id`** carries the risa version character, a cookie hashing the
  modal name and its version (as views do), and the encoded durable fields. If they do not
  fit, building the form raises `StateOverflowError` naming the fields and suggesting
  `risa.Prop`.
- **Each input's `custom_id`** carries the input key and the 4-character prefill
  fingerprint used by `ctx.changed`, plus whatever flags submit decoding needs.
- A `ViewModal` reaches its view through `interaction.message` at submit, using the view's
  normal session machinery; whether that message is current is a live-probe item (§9).
- Unrecognised `custom_id`s are ignored silently; a recognised one that resolves to
  nothing is logged (CONTRIBUTING.md, wire-format rules).

## 7. Decided against

| Alternative | Why not |
|---|---|
| Fields as plain annotations (`name: str`, `risa.Paragraph`) — the design of 2026-10-25 | Cannot carry options, descriptions or runtime data; no place for static text; `str` is ambiguous between text, radio and select |
| Annotated metadata (`Annotated[Sequence[str], risa.CheckboxGroup(options=[...])]`) | Options fixed at class definition; still no static text |
| Components as class attributes (discord.py / miru style) | Mixes look and result in one object; runtime data enters by mutating in `__init__`; the opposite of how views work |
| Fields hold the answers, `render()` binds nodes to fields | The same instance means "what the bot passed in" at open and "what the user answered" at submit; rejected by the maintainer |
| An automatic form for text-only modals plus `render()` for the rest | Two systems to learn, the same settings in two places, a cliff at the first checkbox |
| A separate result class (`on_submit(self, ctx, form: RenameForm)`) | Two classes per form; pyright sees `RenameForm.name` as a plain `str`, so the binding in `render()` is unchecked |
| Answers as `on_submit` parameters | `render()` would have to name them by string |
| Optionality only in the key type, read at runtime from `__orig_class__` | Works (probed on 3.13 and 3.15) but unnecessary once pyright checks the pair |
| A version token on the form with a conflict hook (old §9, "V3/V4") | Edits only what the user changed instead; `ctx.changed` plus an opt-in durable old value covers the real cases |
| Modals unregistered, identity riding the submit handler's token, `carry=` (old §9) | The modal handles its own submit, so it needs its own identity; durable fields replace `carry=` |
| `prompt_wait` (inline `await` for the submit) | Discord forbids a modal in answer to a submit, so a wizard cannot exist anyway; the rendezvous is process-local; every resume mechanism turns idiomatic captures into wrong-row writes |
| Converting text input | §4.4 |
| Always rerendering at the end of `ctx.origin()`, even unchanged | A second rule next to clicks, which rerender only when the state changed; `defer=UPDATE` answers an unchanged submit the same way for both |
| A gone origin as a plain error, logged at ERROR, with no hook | Closing the view, a deploy and a view swap are routine races while a form is open, not programming errors |
| Building now on hikari 2.6 with legacy text inputs | Would ship only text inputs; the maintainer chose to wait (§2) |

Check-then-act across a form (claim, then confirm) is not atomic in any design: the gap is
human think-time, which the locking law forbids holding a lock across. The honest pattern
is to re-check inside `ctx.origin()`; `ctx.reserve` stays deferred.

## 8. Verified so far

### 8.1 Typed input keys (pyright 1.1.414 strict, Python 3.13; msgspec 0.22; ruff)

A stand-alone model of §4–5 (`Input[T]` with `__set_name__`, invariant in `T`; the nodes
with the `required` overloads; `ModalContext.value[T](key: Input[T]) -> T`; the class
family on `msgspec.Struct`, `kw_only=True`) produced no error on correct code and exactly
one error each for:

1. a positional constructor argument;
2. an input key passed to the constructor;
3. `TextInput(Input[str | None])` without `required=False`;
4. `TextInput(Input[str], required=False)`;
5. `Checkbox(Input[str])`;
6. `CheckboxGroup(Input[bool], ...)`;
7. a field value where a key is expected (`TextInput(modal.current)`);
8. a key where a value is expected (`poll.options[0] = modal.name`);
9. an optional result assigned to `str`.

At runtime msgspec treats only annotated attributes as fields (`__struct_fields__` was
`('index', 'current')`), `__set_name__` ran for every key, and encoding touched only the
fields. ruff raised nothing about unannotated `Input` attributes in a Struct body.

Implementation note: with PEP 695 syntax, variance is inferred from use, so `Input` must
use `T` in an invariant position; otherwise `Input[str]` would be accepted where
`Input[str | None]` is required.

### 8.2 Context and class family (pyright strict)

- Today's `Context[T]` used bare raises `reportMissingTypeArgument`; `Context[A | B]`
  accepts a `ComponentContext` (T is inferred covariant).
- A generic mixin fixed in `Context` and re-specialised in a subclass keeps the first
  specialisation (`interaction` stays `A | B`): rejected.
- A `type Context = Mixin[A | B]` alias and a plain abstract base with property overrides
  both work on 3.12; the 3.13 default (`class Context[T: A | B = A | B]`) works and was
  chosen.
- `ViewModal` as a subclass of `Modal` with a narrower `on_submit` context: "overrides
  class Modal in an incompatible manner".
- The `BaseModal[C]` family: `build_modal(ViewModal)` rejected; `prompt` accepts both
  (typed as `BaseModal[ViewModalContext[Never]]`); a `ViewModal[Poll]` whose `on_submit`
  takes `ViewModalContext[Quiz]` rejected; `ViewModal[Poll | Quiz]` with `ctx.origin()` and
  `match` narrows.

## 9. Live probe before building

Against a real Discord application, with the hikari version risa will depend on:

1. The modal's `custom_id` and every input's `custom_id` come back byte-exact.
2. An untouched text input comes back byte-exact, including whitespace and `\r\n`
   (`ctx.changed` depends on it).
3. Whether `interaction.message` at submit is current or the snapshot from when the form
   opened.
4. Whether an unanswered or failed submit keeps the form open with the typed text.
5. Whether `DEFERRED_MESSAGE_UPDATE` is really rejected for a command-opened modal.
6. Text Display and Label together in one modal, and how many top-level components fit.
7. What an unselected optional radio group, an empty checkbox group and an unticked
   checkbox submit.

A failure in 2, 3 or 4 changes this design; come back to it before planning.

## 11. Build order, once hikari lands

Each step lands green under `uv run --group nox nox`.

1. **Live probe** (§9) on the hikari release; revise this document if 2–4 fail.
2. **Python 3.13 floor** (§5.1), on its own.
3. **Context family** (§5.2): the default type parameter, the edit mixin, hooks on bare
   `risa.Context`.
4. **Inputs, `Form` and the modal nodes** (§4.2, §4.4) with the build pass for forms.
5. **`@risa.modal`, the registry, `BaseModal`/`Modal`/`ViewModal`, the wire format** (§4.3,
   §5.3, §6).
6. **Opening:** `client.build_modal`, `ComponentContext.prompt` with the watchdog rule
   (§4.5).
7. **Submit dispatch:** routing, `ModalContext`, `ctx.value`, `ctx.changed`, DI, errors,
   the `defer` knob, `on_outdated` (§4.6, §4.8, §4.9). On the REST transport the modal
   listener shares hikari's slot the way the component listener does since #44 (§4.5).
8. **`ViewModal`:** `ViewModalContext`, `ctx.origin()`, the hook routing including the
   origin-gone case (§4.7).
9. **testbot:** a command-opened form and a view-opened form with every node hikari
   supports.

The detailed implementation plan is written against the hikari release, once its API is
final.
