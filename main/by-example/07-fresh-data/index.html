Fresh data with Prop and load()¶

Some things should be read fresh on every click instead of saved in the message, such as a database row. Mark them risa.Prop and fill them in load().

A leaderboard¶

game is a field like any other, saved in the message. rows is a risa.Prop, and load() fills it. Scores stands in for your database, and you can find it in the full file.

@risa.register(name="leaderboard")
class Leaderboard(risa.View):
    game: str = "chess"
    rows: risa.Prop[list[str]] = msgspec.field(default_factory=list[str])

    async def load(self, scores: Scores) -> None:
        self.rows = await scores.top(self.game)

load() names Scores as a parameter, as a handler would, and main() registers it. Without that, client.build raises linkd's DependencyNotSatisfiableException. msgspec.field(default_factory=list[str]) gives each view a new empty list.

render() reads a prop as it reads a field. Each game's button runs switch, and _TOP at the top of the file holds each game's top players.

def render(self) -> ui.Layout:
    lines = [f"{n}. {name}" for n, name in enumerate(self.rows, start=1)]
    buttons = [
        ui.Button(
            risa.bind(self.switch, game),
            label=game.title(),
            disabled=game == self.game,
        )
        for game in _TOP
    ]
    return ui.Container(
        ui.TextDisplay(f"## Top players in {self.game}"),
        ui.TextDisplay("\n".join(lines)),
        ui.Row(*buttons, ui.Button(self.refresh, label="Refresh")),
    )

What a prop costs¶

A prop takes no room in the message: nothing about rows goes into the buttons' ids, however many rows load() returns. It needs a default, because each click builds the view with its props at their defaults before load() runs, and without one @risa.register raises ViewDeclarationError.

A prop is never saved, so what a handler puts in one lasts for that click's rerender, and the next click starts from the default again.

When load() runs¶

  1. 1Fields returnFrom the message.
  2. 2load()Fills the props.
  3. 3The handlerChanges fields.
  4. 4rerender()Draws fields and props.

client.build runs it too, before render(), so the first message has its rows. On a click, refresh only rerenders, and the rows are new because load() has just read them. A handler can leave load() out.

@risa.handler
async def refresh(self, ctx: risa.ComponentContext) -> None:
    await ctx.rerender()

load() runs inside the three seconds from Answering in time, and its time counts toward auto-defer's 2 seconds.

A handler that changes what load() reads¶

load() runs before the handler, and not again.

A handler that sets self.game and calls ctx.rerender() draws the new heading over the old rows, because load() read them while game still held the old value.

Read them in the handler. load() would still read the old game's rows first, for nothing, so switch is made with load=False. It takes the game as a wire argument, as in Handlers and arguments, and after it scores, which risa injects as it does for load(). A handler's injected parameter needs no default.

@risa.handler(load=False)
async def switch(
    self,
    ctx: risa.ComponentContext,
    game: str,
    scores: Scores,
) -> None:
    self.game = game
    self.rows = await scores.top(game)
    await ctx.rerender()

A handler that needs no load()¶

@risa.handler(load=False) keeps load() from running for clicks on that handler. It suits a handler that fills the props itself, as switch does, and one that uses no prop at all, such as one that deletes the message.

The handler then gets the props at their defaults, and so does every rerender of that click: a ctx.rerender() in the handler, and the one risa does itself when the handler changed a field without rerendering. Fill every prop render() draws, or change no field and leave the rerender out. client.build still runs load().

A change with no click¶

A message shows what load() read when it was last drawn. When the data changes with no click, such as a score that comes in from elsewhere, client.rerender redraws the message. The view's fields stay as they are, and load() reads the rows again.

boards: dict[hikari.Snowflake, hikari.Snowflake] = {}

@bot.listen()
async def on_message(event: hikari.GuildMessageCreateEvent) -> None:
    if event.content == "!leaderboard":
        rendered = await client.build(Leaderboard())
        message = await rendered.send_to(bot.rest, event.channel_id)
        boards[event.channel_id] = message.id
    if event.content == "!scored" and event.channel_id in boards:
        await SCORES.win("chess", "Sam")
        await client.rerender(event.channel_id, boards[event.channel_id], Leaderboard)

SCORES is the Scores the bot registered, and win stands in for whatever changes your data. rerender takes the channel, the message and the view's class, so keep the id of the message send_to returns. The example keeps it in a dict; your bot would keep it beside the data. For a view sent in answer to an interaction, fetch the message once with Response.fetch to learn its id.

To change a field as well, open the view with client.open. The block gets the view with its fields as they are now. Leaving the block redraws the message and saves the state, and a block that raises draws nothing and saves none of its changes. The same listener goes on:

if event.content == "!go" and event.channel_id in boards:
    rows = await SCORES.top("go")
    message_id = boards[event.channel_id]
    async with client.open(event.channel_id, message_id, Leaderboard, load=False) as view:
        view.game = "go"
        view.rows = rows

load() runs before the block, as it runs before a handler. This update changes game, which load() reads. So the example reads the new rows itself and then opens the view with load=False. When the block changes nothing that load() reads, leave load=False out.

A redraw and a block are both updates of the message, and what follows holds for either. No hook and no error handler runs for an update, and load() runs in DEFAULT alone, as it does in client.build.

Which call for which view¶

The view To redraw its message
Fields, and buttons or menus client.rerender, or client.open to change a field too
No fields client.rerender, or client.open to fill a prop in the block. risa fetches nothing, takes no lock, and does not check what the message shows
Fields, and a render() that never draws a button or a menu rest.edit_message(channel, message, **await client.build(view)), where view is a new instance with its fields passed again

A message with nothing to click holds no state, which is why the last row builds a new view.

Do not edit the message of a view from the first row through rest.edit_message.

risa remembers the state it last saved to a message, and after an edit it did not make, a later click can bring that state back. A view in a store gets a second record, and the first stays until its ttl runs out, or for good under ttl=None. Use rerender or open for such a view.

What an update costs¶

For a view with fields:

  • A fetch. risa fetches the message to find the view's state, so the bot needs View Channel and Read Message History in the channel. A view in a store costs a second fetch: the message names the record, and risa reads the message again once it holds that record's lock.
  • The view's lock. Clicks on the message wait until the update is done, and Discord's three seconds keep running for them. load() and the block run under the lock, so do slow work before open, as the example does with the rows. When the data changes often, update a message every few seconds at most: Discord limits how fast a bot edits messages, and an edit that waits for that limit holds the lock.

An update also restarts the ttl of a view in a store and the time expires_after counts, so a board that is redrawn every minute never expires.

The limits of an update¶

  • A handler of the same message. The handler holds the lock open waits for, so open raises LockTimeoutError after 10 seconds. Change self there and call ctx.rerender().
  • An ephemeral message. Only an interaction can edit it: the one that sent it, or a click on it.
  • A layout from ctx.edit. An update draws what render() returns, as ctx.rerender() does, so a layout a handler drew with ctx.edit is gone after it. A layout with nothing to click ended the view, and the update raises MessageOutdatedError, as it does once ctx.replace gave the message to another view. A view without fields is not checked, so an update draws it over whatever the message shows.
  • Several processes. Several processes says what an update does when clicks land in another process.

What an update raises¶

Where a click would run on_outdated because the state no longer fits the fields, or on_state_missing, there is no click to answer, so open and rerender raise:

  • MessageOutdatedError when the message holds no state of the view that this code can read: it shows another view or another version of this one, it has nothing to click, or a breaking change to the view's fields or its placement went out without a raised version. Catch it to stop updating a message whose view has ended. A view without fields never raises it.
  • StateNotFoundError when the record of a view in a store is gone.
  • LockTimeoutError when a click holds the view's lock for more than 10 seconds.
  • hikari's NotFoundError for a message that was deleted, and its ForbiddenError for one the bot may not read. risa passes them on as they are.

What the edit raises passes through as well. A view in the message has saved nothing then, so run the block again. A view in a store has saved the new state, and the block would apply its change a second time: call client.rerender to draw what is saved.

Leaving the block can raise as ctx.rerender() can, with StateOverflowError when the state no longer fits the message and StateConflictError when another process saved first. After a conflict the block is over, so run open again. The reference of client.open lists everything it raises.

"""A field for what to show, and a prop for what the database says right now."""

from __future__ import annotations

import asyncio
import os

import hikari
import msgspec

import risa
from risa import ui

_TOP = {
    "chess": ["Mika", "Jo", "Sam"],
    "go": ["Noor", "Mika", "Ren"],
}


class Scores:
    async def top(self, game: str) -> list[str]:
        await asyncio.sleep(0.1)
        return _TOP[game]

    async def win(self, game: str, player: str) -> None:
        await asyncio.sleep(0.1)
        _TOP[game].remove(player)
        _TOP[game].insert(0, player)


SCORES = Scores()


@risa.register(name="leaderboard")
class Leaderboard(risa.View):
    game: str = "chess"
    rows: risa.Prop[list[str]] = msgspec.field(default_factory=list[str])

    async def load(self, scores: Scores) -> None:
        self.rows = await scores.top(self.game)

    def render(self) -> ui.Layout:
        lines = [f"{n}. {name}" for n, name in enumerate(self.rows, start=1)]
        buttons = [
            ui.Button(
                risa.bind(self.switch, game),
                label=game.title(),
                disabled=game == self.game,
            )
            for game in _TOP
        ]
        return ui.Container(
            ui.TextDisplay(f"## Top players in {self.game}"),
            ui.TextDisplay("\n".join(lines)),
            ui.Row(*buttons, ui.Button(self.refresh, label="Refresh")),
        )

    @risa.handler
    async def refresh(self, ctx: risa.ComponentContext) -> None:
        await ctx.rerender()

    @risa.handler(load=False)
    async def switch(
        self,
        ctx: risa.ComponentContext,
        game: str,
        scores: Scores,
    ) -> None:
        self.game = game
        self.rows = await scores.top(game)
        await ctx.rerender()


def add_dependencies(client: risa.Client) -> None:
    registry = client.di.registry_for(risa.Contexts.DEFAULT)
    registry.register_value(Scores, SCORES)


def main() -> None:
    bot = hikari.GatewayBot(
        os.environ["DISCORD_TOKEN"],
        intents=hikari.Intents.ALL_UNPRIVILEGED | hikari.Intents.MESSAGE_CONTENT,
    )
    client = risa.client_from_app(bot)
    add_dependencies(client)
    client.add_view(Leaderboard)

    boards: dict[hikari.Snowflake, hikari.Snowflake] = {}

    @bot.listen()
    async def on_message(event: hikari.GuildMessageCreateEvent) -> None:
        if event.content == "!leaderboard":
            rendered = await client.build(Leaderboard())
            message = await rendered.send_to(bot.rest, event.channel_id)
            boards[event.channel_id] = message.id
        if event.content == "!scored" and event.channel_id in boards:
            await SCORES.win("chess", "Sam")
            await client.rerender(event.channel_id, boards[event.channel_id], Leaderboard)
        if event.content == "!go" and event.channel_id in boards:
            rows = await SCORES.top("go")
            message_id = boards[event.channel_id]
            async with client.open(event.channel_id, message_id, Leaderboard, load=False) as view:
                view.game = "go"
                view.rows = rows

    bot.run()


if __name__ == "__main__":
    main()
